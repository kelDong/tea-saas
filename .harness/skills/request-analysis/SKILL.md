# SKILL: 需求分析

> 目的：把模糊想法转成可评审、可开发的需求。产出 PRD 级文档。

## 适用场景

接到一个新功能/模块需求时。

## 流程

1. **明确角色与范围**：谁用（总部/加盟商/店长/顾客）、解决什么痛点、MVP 是否要做
2. **写用户故事**：`As a 角色 / I want 功能 / So that 价值` + 验收标准（AC）
3. **写功能编号**：`F-<模块>-<序号>`（如 F-ORD-02），后续数据库/接口/测试全部引用
4. **确认验收标准**：AC 必须可测试、无歧义（尽量量化）
5. **检查闭环**：这个功能前后依赖是否完整（如"上架"依赖"产品库"与"库存"）
6. **更新权限**：明确哪个角色可看/可操作（更新权限矩阵）

## 输出模板

```
**F-XXX-序号 名称**
- 用户故事：...
- AC：...
- 决策/关联：...（引用决策记录或 PRD 编号）
```

## 检查清单

- [ ] 有明确角色 + 验收标准
- [ ] 有功能编号，后续文档引用一致
- [ ] 不违反已定决策（如一期不做 MQ、只整单退款）
- [ ] 涉及多租户/权限的，已更新矩阵
