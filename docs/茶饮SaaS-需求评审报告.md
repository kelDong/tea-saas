## 1. 评审结论

**逻辑主干成立，但存在 5 个阻断级缺口，当前 PRD 不能直接进入开发。**

- 需求主线（研发配方 → 上架 → 采购 → 点单扣库存 → 支付 → 报表）闭环 ✅
- 多租户 + BOM 库存模型设计合理 ✅
- **但供应链闭环有断点**：只定义了"加盟商→总部"的采购，**总部→供应商的集采采购缺失**
- **门店端缺"线下收银"**：PRD 只覆盖线上点单，真实门店的现金/线下收款场景未定义
- **权限矩阵有一处与多租户隔离冲突**：平台管理员（R1）对租户业务数据全权可见可操作

## 2. P0 阻断级问题（必须决策后才能进开发）

### P0-1 门店端缺"线下收银"（现金/线下收款）

- **现状**：PRD 订单模块只定义"顾客小程序下单"（F-ORD-01），门店端只有接单/制作/核销线上订单（F-ORD-03）。标题与原型都叫"接单收银"，但**没有收银功能**。
- **问题**：真实奶茶店大量场景是顾客到店现金/扫码付款，店员需要在门店端**手工创建订单收款**。缺这个能力，"收银"名不副实，种子门店无法使用。
- **需要决策**：MVP 是否做"门店端手工下单收款"（支持现金/微信扫码收款码）？建议 **MVP 必做简版**（手工加购→收款→入账），扫码收款对接微信 Native 支付。

### P0-2 供应链闭环断点：总部→供应商的集采采购缺失

- **现状**：F-SUP-03/04 只覆盖"加盟商→总部"采购；规划书职责写了总部"原料集采"，但**没有总部向供应商采购的需求**。
- **问题**：供应链链路是"供应商→总部→加盟商"，缺了第一段。总部仓（或直接分拨）的入库流程、总部仓库存模型均未定义。数据库只有门店库存表（`inv_store_material_stock`），**没有总部仓库存表**。
- **需要决策**：
  - A) 总部不建仓：供应商直发门店（总部只维护价格与下单），MVP 最简单
  - B) 总部建中心仓：加"总部库存"概念与"总部→门店调拨"
  - 建议 MVP 选 A，二期再上中心仓。

### P0-3 平台管理员（R1）权限与多租户隔离冲突

- **现状**：权限矩阵 5.2 中，R1 对**所有业务菜单**（原料档案、配方 BOM、订单、会员、优惠券…）均为 ✅（可见可操作）。
- **问题**：平台管理员能看到/操作任意租户的业务数据，与多租户隔离（第 6 章"平台侧 vs 业务侧"）矛盾；也是安全隐患（一个操作失误影响客户数据）。
- **需要决策**：平台管理员对租户业务数据应为——
  - A) **只读审计**（可看不可改，用于客服/支持）——建议
  - B) 完全不可见（仅平台自身管理功能）
  - C) 维持全权（不推荐，违反隔离原则）

### P0-4 储值支付通道未定义

- **现状**：F-MEM-03 说"储值可支付订单"；门店端日结原型也列了"储值支付"金额；但支付模块（F-PAY-01）只定义了微信支付。
- **问题**：储值支付走什么流程？`ord_order.pay_channel` 的取值、储值扣款与微信支付的组合、退款时储值部分退回哪里（原路退回储值账户 vs 微信）——均未定义。
- **需要决策**：MVP 是否同时支持"微信支付 + 储值支付"两种通道？建议保留，但**明确储值余额不足时不能混合支付**（一期不做混合，简化退款逻辑）。

### P0-5 退款金额拆分规则未定义

- **现状**：F-PAY-02 只写"退款原路退回 + 回补库存"；但订单可能同时用了优惠券 + 积分 + 储值 + 微信支付（F-MKT/F-MEM/F-PAY 交叉）。
- **问题**：混合支付的订单退款怎么拆？部分退款时优惠券/积分/储值/微信各退多少？规则不定义，实现时必然返工。
- **需要决策**（建议 MVP 简化）：
  - 一期**只支持整单退款**，不支持部分退款
  - 退款顺序：优先退储值部分 → 微信部分原路退回；**已核销的券不退还**（明确写入 AC）

| P1-4 | 支付回调"MQ + 重试"与单体架构未对齐 | 非功能需求写了 MQ | 单体一期用"本地表 + 定时重试"即可，MQ 二期；需与规划书选型一致 |

| P1-6 | 超时未付自动取消时长未定 | F-ORD-02 提到超时取消 | 明确默认 15 分钟，超时回补库存（写入配置项） |
