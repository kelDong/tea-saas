## 1. 项目概述

### 1.1 背景与痛点

- 中小茶饮连锁品牌（5–50 家门店，直营 + 加盟混合）普遍存在：
  - 总部管不住门店：产品标准（配方）无法统一，加盟商各自为政
  - 供应链分散：原料各店自采、价格不统一、无分级定价
  - 库存靠人工盘点：畅销品断货、滞销品积压，顾客点单时才知道卖完了
  - 经营数据分散，总部无法实时掌握各门店经营与库存
- 市面上通用收银 SaaS（美团、客如云）侧重单店收银，**缺少"总部产品研发 + 供应链 + 加盟商管理"的连锁经营能力**

### 1.2 项目目标

| 目标 | 衡量标准 |
|---|---|
| 跑通完整业务闭环 | 总部研发配方 → 加盟商上架采购 → 顾客点单（BOM 扣库存）→ 支付接单 → 总部报表 |
| 拿到种子客户 | 上线 3 个月内入驻 1–2 个品牌（共 5–20 家门店，含加盟店） |
| 多租户可扩展 | 新品牌入驻无需改代码，自助开通 |
| 库存准确 | 下单扣减库存后，顾客端"可售"状态与实际原料库存一致 |

### 1.3 非目标（本期不做，明确排除）

- 外卖平台（美团/饿了么）对接
- 复杂促销（拼团、秒杀、直播带货）
- 仓储物流、跨区域多仓调拨
- 原料供应商的在线自助供货平台（本期由总部人工管理供应商）
- 财务/税务对接

## 2. 商业模式与目标客户

### 2.1 商业模式

- **SaaS 订阅制**：卖给**品牌总部**，按门店数按月收费（如 99–299 元/店/月，按功能档位）
- **增值服务**：供应链集采撮合（总部通过平台采购原料，平台可收取服务费）、经营数据报告
- 起步期：前 1–2 家种子品牌**免费试用换反馈**，打磨产品与案例

### 2.2 目标客户画像（首期）

- **形态**：有 5–20 家直营 + 加盟门店的区域茶饮品牌，总部有专人负责产品/供应链
- **痛点核心**：产品标准不统一、原料采购分散、库存靠人工、加盟商难管理
- **决策人**：品牌老板/运营负责人
- **首批获取渠道**：本地餐饮设备商、原料供应商转介绍，小红书/抖音茶饮经营内容获客

### 2.3 客户价值主张

> 总部一个后台管产品、管供应链、管加盟商；加盟商一部手机开好店；顾客看到的就是能做的。

## 3. 业务模型与角色职责

### 3.1 组织与租户模型

```
平台管理员（超级租户）—— 管理品牌入驻、套餐、全局配置
   └── 品牌商（租户，隔离单位；决策：租户=品牌，总部管理加盟商）
         ├── 总部（品牌最高权限）
         │     ├── 直营门店（总部自有，不挂加盟商）
         │     └── 加盟商 A ── 门店 A-1 / 门店 A-2（加盟商可多店，1:N）
         ├── 加盟商 B ── 门店 B-1 / 门店 B-2
         └── 顾客（会员，归属品牌，可跨门店消费）
```

- **租户边界 = 品牌**：总部的产品库、供应链、加盟商、顾客全部隔离在品牌租户内
- **门店归属**：门店挂加盟商或总部（直营），总部统一评定加盟商等级
- **数据权限**：总部看全局；加盟商只能看自己门店的数据；店员只能看本店

### 3.2 角色职责清单（业务需求确认）

| 角色 | 使用端 | 职责 |
|---|---|---|
| 平台管理员 | Web 管理后台 | 品牌入驻、套餐计费、全局配置、平台数据看板 |
| 总部（老板/产品研发/供应链/运营） | Web 管理后台 | **产品研发**：定义产品配方 BOM；**供应链**：原料集采、维护供应商、制定分级价格；**加盟商管理**：门店档案、等级评定；**全局统计**：各门店经营与库存数据 |
| 加盟商 | Web 管理后台 / 门店端 | 从总部产品库选择上架商品；管理门店原料库存；按需向总部采购原料；处理顾客订单；查看本店经营数据 |
| 店长/店员 | 门店端（Web/平板） | 接单、制作、核销、门店日结 |
| 顾客 | 微信小程序 | 选择最近门店；浏览有库存商品并下单；查看历史购买记录 |

## 4. 项目范围（MVP 界定）

### 4.1 MVP 功能清单

| 模块 | 本期功能（必做） | 二期（暂缓） |
|---|---|---|
| 租户与权限 | 品牌/总部/加盟商/门店四级、RBAC、员工管理 | 加盟商独立结算权限 |
| **产品研发（BOM）** | 原料档案、配方 BOM（原料×用量）、商品=配方+规格+定价、发布到产品库 | 配方版本管理与试算 |
| **供应链** | 供应商档案、原料集采入库、**分级价格表**（按加盟商等级定价）、采购单（加盟商→总部） | 供应商自助平台、自动补货建议 |
| **加盟商管理** | 加盟商档案、**等级评定**、门店档案（加盟/直营） | 加盟政策模板、合同管理 |
| **门店库存** | 门店原料库存台账、采购入库、**BOM 反算扣减**、库存预警（低库存提醒） | 盘点单、损耗登记、跨店调拨 |
| 商品上架 | 加盟商从产品库选择上架、总部审核 | 门店级价格调整 |
| 订单 | 下单（校验库存）、状态机、接单、取餐码 | 预点单、配送 |
| 支付 | 微信支付 V3、退款、回调幂等 | 对账自动化深度 |
| 会员 | 会员档案、等级、积分、储值 | 付费会员卡 |
| 营销 | 优惠券（满减/折扣）、发券核销 | 拼团、秒杀、裂变 |
| 报表 | 门店日报/周报、品牌汇总看板、**库存统计** | 多维分析、导出定制 |
| 基础 | 登录认证、操作日志、数据字典 | 消息通知中心 |

### 4.2 验收标准（上线门槛）

- [ ] 总部端闭环：建原料 → 建配方 BOM → 发布商品 → 建供应商/分级价格 → 开通加盟商
- [ ] 加盟商端闭环：上架商品 → 提交采购单 → 入库 → 接单制作
- [ ] 顾客端闭环：选门店 → 只看到有库存商品 → 下单 → 支付 → 取餐
- [ ] **库存联动验证**：售出 N 杯后原料库存精确扣减；原料不足时该商品在顾客端自动禁售
- [ ] 多租户隔离验证：A 品牌看不到 B 品牌任何数据；加盟商看不到其他加盟商数据
- [ ] 支付链路：沙箱 + 正式环境各跑通一次全流程

## 5. 总体技术方案

### 5.1 架构定位：模块化单体（Modular Monolith）

- 单项目 Maven 多模块，一个可部署单元，一期**不上微服务**
- 理由：个人全栈资源有限，微服务的分布式事务、服务治理会拖垮 MVP
- 注意：BOM 扣库存涉及"订单 + 库存"一致性，单体事务/本地锁即可解决，这也是不上微服务的重要理由

### 5.2 多租户模型（核心主线）

- 隔离方案：**共享库 + `tenant_id` 字段**，MyBatis-Plus 租户插件自动拼 SQL
- `tenant_id` 挂在品牌商一级；`store_id` 二级维度；加盟商用 `franchisee_id` 归属关联
- 数据权限层：总部=全部门店；加盟商=名下门店；店员=本店

### 5.3 Maven 模块划分（v1.1 更新）

```
tea-saas (父POM)
├── tea-common        # 工具类、常量、统一返回/异常
├── tea-framework     # 安全、MyBatis-Plus、Redis、租户拦截器
├── tea-system        # 租户、用户、角色、菜单、权限（地基核心）
├── tea-franchise     # 加盟商、等级评定、门店档案【新】
├── tea-supply        # 原料、供应商、采购单、分级价格【新】
├── tea-bom           # 配方 BOM、原料用量【新】
├── tea-product       # 商品、分类、规格、产品库、加盟商上架
├── tea-inventory     # 门店原料库存、BOM 反算扣减、库存预警【新】
├── tea-order         # 订单、状态机（下单时联动库存）
├── tea-payment       # 支付、退款、回调
├── tea-member        # 会员、积分、储值
├── tea-marketing     # 优惠券、活动
├── tea-report        # 报表、看板（经营 + 库存）
├── tea-job           # 定时任务（起步用 @Scheduled）
└── tea-server        # 启动模块（聚合入口）
```

**模块依赖方向**（自下而上，防止循环依赖）：
`common → framework → system → { bom, franchise, supply } → { product, inventory } → { order, payment, member, marketing, report } → server`

### 5.4 技术选型明细

| 类别 | 选型 | 说明 |
|---|---|---|
| 语言/框架 | JDK 17 + Spring Boot 3.x + Maven | 多模块基础 |
| ORM | MyBatis-Plus + TenantLineInnerInterceptor | 多租户自动拼 SQL 核心 |
| 认证权限 | Sa-Token | 轻量，个人开发体验好 |
| 缓存/锁 | Redis | 会话、验证码、**库存扣减分布式锁/乐观锁** |
| 数据库 | MySQL 8 | 金额用"分"存整数，订单号雪花 ID |
| 文件存储 | 本地起步 → 后期 OSS | 减少前期依赖 |
| 定时任务 | Spring `@Scheduled` | 需要时再上 XXL-Job |
| 管理后台 | Vue3 + Vite + Element Plus + Pinia | 动态路由 + 按钮级权限 |
| 顾客端 | uni-app（Vue3 语法） | 一套代码多端可扩展 |
| CI/CD | GitHub Actions / GitLab CI | 提交 → 测试 → 构建 → 部署 |
| 部署 | Docker Compose 起步 | 规模上来再上 K8s |
| 监控 | Prometheus + Grafana、SkyWalking、ELK/Loki | 指标、链路、日志 |

### 5.5 关键工程要求（自研路线的生存底线）

1. **地基冻结**：第 12 周后，权限/租户代码只修 bug，不再加功能
2. **随时可跑**：每完成一个模块，`tea-server` 必须能启动、接口能调通；禁止"攒着一起联调"
3. **代码生成器先行**：第 5–6 周写简单生成器（entity/mapper/service/controller），后续模块省 60% 时间
4. **统一规范**：统一返回结构、异常处理、日志埋点、参数校验
5. **库存一致性优先**：BOM 扣减相关代码单独设计、单独测试，不允许被业务赶工破坏

## 6. 核心业务流程（BOM 库存联动）

这是本系统区别于普通收银 SaaS 的核心能力，单独成节。

### 6.1 库存模型

- 库存单位为**原料**（如"红茶 500g/包、珍珠 1kg/包、杯盖 1 个"），库存挂在**门店**维度：`store_material_stock`
- 每个商品（饮品）由**配方 BOM** 定义：`饮品 = 原料 × 用量`（如"珍珠奶茶 = 红茶 20g + 奶精 30g + 珍珠 50g + 杯 1 个 + 封口膜 1 张"）
- 商品可售 = 该门店所有原料库存 ≥ 配方用量

### 6.2 下单扣库存流程

```
顾客选门店 → 查看商品（仅返回"有库存"商品）→ 提交订单
    ↓
服务端：按 BOM 计算每原料所需用量 = 配方用量 × 购买数量
    ↓
校验：该门店各原料库存是否充足（不足则整单拦截/提示）
    ↓
扣减库存（Redis 预扣 + 数据库乐观锁/事务，防超卖）
    ↓
生成订单 → 微信支付 → 门店接单 → 制作 → 核销取餐
    ↓
（制作/核销可回补或确认扣减，采用"下单即扣"简单模型）
```

### 6.3 采购与入库流程（加盟商 → 总部）

```
加盟商看本店原料库存（含预警）→ 按需生成采购单（选原料+数量）
    ↓
总部接单 → 按分级价格表计价 → 确认发货（或线下供货后确认）
    ↓
加盟商收货入库 → 原料库存增加 → 可售商品恢复
```

### 6.4 关键一致性设计

| 问题 | 方案 |
|---|---|
| 超卖 | Redis 预扣 + MySQL 事务内乐观锁（`version` 或库存 `WHERE stock >= need`） |
| 库存不足的并发 | 扣减失败即回滚订单，提示"原料不足" |
| 下单与扣库存原子性 | 同一本地事务内完成（单体优势）；二期拆服务时改 MQ 补偿 |
| 支付超时未付 | 定时任务释放预扣库存（下单即扣 + 超时回补） |
| 负库存 | 数据库层禁止负值 + 每日库存对账脚本 |

## 8. 里程碑与时间表

> **v1.2 校准（vibe coding 模式）**：原 v1.1 按"个人全栈手写 6–7 个月"估算，已不适用。实际 M1（立项→需求→评审→数据库→原型→harness）仅约 **3 小时**完成，开发阶段由 AI 编码工具按 `.harness/` 与 `docs/` 推进。**瓶颈从"编码速度"转移到"业务验证/资质/客户"**，因此时间表以周为单位、以验证环节为节奏。
> 前提：种子品牌访谈（M1 缺口）、微信支付/小程序资质并行启动。

```
M1（已完成 · 约 3 小时）✅ 立项 + 需求 + 设计定稿
                 ├─ 规划书 v1.1 / PRD v1.1 / 数据库设计 v1.1 / 工程规范 v1.1
                 ├─ 需求评审（P0×5 + P1×6 全部拍板）
                 ├─ 三端可点击原型 v1.1 + 架构图
                 ├─ .harness/ 项目 AI 协作规范（16 文件）
                 └─ ⚠️ 缺口：种子品牌访谈未做（P2 项待访谈确认）

M2（第 1–3 周） 地基搭建（vibe coding 加速）
                 ├─ 父 POM + 15 模块骨架 + Enforcer/Checkstyle
                 ├─ tea-common/framework（Result/异常/租户插件/Sa-Token）
                 ├─ tea-system（租户/用户/角色/菜单/权限）
                 ├─ 代码生成器 + 后台前端骨架
                 └─ 并行：种子品牌访谈启动（补 M1 缺口）

M3（第 3–8 周） 业务闭环（核心）
                 ├─ bom / franchise / supply → product / inventory
                 ├─ order（BOM 扣库存）/ payment / member / marketing / report
                 ├─ 后台业务页面（总部 + 加盟商）+ 小程序点单闭环
                 ├─ 全链路联调：研发配方 → 上架 → 采购入库 → 点单扣库存 → 支付 → 接单 → 报表
                 └─ 微信支付资质 / 小程序类目审批完成

M4（第 9–12 周）种子店试运营（节奏由客户验证决定）
                 ├─ 1–2 家品牌、5–20 家门店真实上线
                 ├─ 测试修复（库存并发 / 支付 / 对账重点）
                 └─ 总部报表与库存统计验收

M5（第 13 周起） 复制推广
                 ├─ 第 3–10 家品牌入驻
                 ├─ 营销模块深度（拼团/秒杀）
                 └─ 二期：加盟结算、供应商自助平台、盘点调拨
```

**资源投入预估（vibe coding 模式，编码加速但验证不加速）**：MVP 到种子店上线约 **10–12 周**；其中编码约 5–6 周，**资质办理 2–4 周、种子验证 2–3 周为不可压缩环节**。完整商业版（含二期加盟结算）约 **6–9 个月**。

**关键提醒**：编码不再是瓶颈。M2 开工当天就应启动——种子品牌访谈（补 M1 缺口）与微信支付/小程序资质申请（M3 需要）。这两件事的进度决定真实上线时间，而不是代码。

## 9. 团队与协作方式

- **现状**：个人全栈（后端 + 前端 + 小程序 + 部署 + 运营）
- **必须补齐的外部资源**（可外包/兼职）：
  - UI 设计（1 次性外包小程序高保真 + 后台视觉规范）
  - 测试（上线前找 1 名兼职测试做 UAT，**库存并发场景必须覆盖**）
  - 法务/资质：微信支付商户号、小程序类目资质（餐饮-饮品）提前办理
  - 供应链业务顾问（可选）：种子品牌的总部运营人员本身就是最佳顾问
- **协作规范**：Git 分支模型（main + dev + feature）、PR 评审（哪怕自己评审）、文档同步更新
